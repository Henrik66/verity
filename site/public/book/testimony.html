Chapter 3Truth and Testimony

Every truth in Verity carries testimony. This chapter explains where testimony comes from, how the logical operators combine it, and how because lets you put a claim in your own words.

3.1 What testimony is#

A value of type truth is either a verity or a falsity. Alongside that one bit it carries testimony:

  • a verity's testimony is its witness: why the claim holds;
  • a falsity's testimony is its refutation: why the claim fails.

Testimony is a tree. A comparison is a leaf. Operators like and, and quantifiers like forall, build larger trees out of the testimony of their parts. testimony.explain renders the tree as indented text, with the truth on the first line and each level of the tree indented two more spaces. That format is used throughout the book and summarized in Appendix A.

Testimony is evidence, not decoration. Each kind of node records the facts that actually decided the answer, so reading it from the top down should always tell you why.

3.2 Comparisons#

Comparisons are where most testimony starts. A comparison's testimony quotes the expression as you wrote it, followed by the evaluated operands and the relation that actually held between them:

verity
from testimony import explain

name = "al"
(len(name) >= 3) |> explain |> print
(len(name) == 2) |> explain |> print
output
falsity
  len(name) >= 3: 2 < 3
verity
  len(name) == 2: 2 == 2

When the comparison holds, the relation is the one you wrote. When it fails, it is the opposite one: >= becomes <, == becomes !=, and so on. Showing both the source text and the values is what makes the line useful. The source tells you which check this is, and the values tell you why it came out the way it did.

3.3 Conjunction: and#

p and q is a verity when both sides are. Its testimony depends on which way it went:

  • A verity from and needs every part to hold, so its witness lists all of them under all of:. A chain such as p and q and r is flattened into one list.
  • A falsity from and needs only one failing part. and short-circuits, as in Python, so the refutation is simply the testimony of the first part that failed.
verity
from testimony import explain

def in_range(x) = (x > 0) and (x < 10)

in_range(7) |> explain |> print
in_range(12) |> explain |> print
output
verity
  all of:
    x > 0: 7 > 0
    x < 10: 7 < 10
falsity
  x < 10: 12 >= 10

For in_range(12), the first part held, so it is irrelevant to why the whole thing failed and does not appear. Testimony includes what decided the answer and nothing else.

3.4 Disjunction: or#

or is the mirror image of and:

  • A verity from or needs just one part to hold. It short-circuits, so the witness is the testimony of the first part that held.
  • A falsity from or needs every part to fail, so the refutation lists all of them under none of:.
verity
from testimony import explain

def out_of_range(x) = (x < 0) or (x > 10)

out_of_range(-3) |> explain |> print
out_of_range(7) |> explain |> print
output
verity
  x < 0: -3 < 0
falsity
  none of:
    x < 0: 7 >= 0
    x > 10: 7 <= 10

3.5 Negation: not#

not p flips the truth and keeps the evidence. A refutation of p is exactly a witness for not p, and vice versa:

verity
from testimony import explain

x = 7
(not (x > 10)) |> explain |> print
output
verity
  not:
    x > 10: 7 <= 10

Design note: rendering not

The meaning of not is settled: it swaps witness and refutation. How it prints is a proposal. A not: node wrapping the original testimony keeps the source structure visible. The alternative is to drop the wrapper and print the inner testimony directly, which is shorter but hides that a negation happened.

3.6 Custom testimony: because#

Comparison testimony is precise but low-level. len(name) >= 3: 2 < 3 tells you what happened, not what it means. because attaches a claim in plain words:

verity
p because "the claim p establishes"

The message states the claim, the thing that is true when p is a verity. It renders as witnessed: or refuted: depending on the outcome, with p's own testimony nested beneath it, so the high-level reason and the low-level evidence appear together. Here is a validator built from three claims:

verity
import string_ops
from testimony import explain

def valid_username(name) =
    (len(name) >= 3 because f"{name!r} has at least 3 characters")
    and (len(name) <= 16 because f"{name!r} has at most 16 characters")
    and (string_ops.is_alnum(name) because f"{name!r} is alphanumeric")

for name in ["ada", "al", "grace_hopper"]:
    print(f"{name!r}: {explain(valid_username(name))}")
output
'ada': verity
  all of:
    witnessed: 'ada' has at least 3 characters
      len(name) >= 3: 3 >= 3
    witnessed: 'ada' has at most 16 characters
      len(name) <= 16: 3 <= 16
    witnessed: 'ada' is alphanumeric
      every character of 'ada' is alphanumeric
'al': falsity
  refuted: 'al' has at least 3 characters
    len(name) >= 3: 2 < 3
'grace_hopper': falsity
  refuted: 'grace_hopper' is alphanumeric
    '_' at index 5 is not alphanumeric

Each rule is written once, and the error message falls out of it. Notice the last case. string_ops.is_alnum is a standard library function that returns a testifying truth, so its refutation names the offending character and its position.

Because the message is the claim, phrase it as a statement that is true when the check passes: "has at least 3 characters", not "is too short". The same message then reads correctly after both witnessed: and refuted:.

Design note: precedence and laziness

Two details are still open. First, precedence: the examples always parenthesize p because msg when it is combined with and/or, and until the grammar settles, you should too. Second, evaluation: it is proposed that the message, often an f-string, is evaluated only if the testimony is observed. That way a because on a hot path costs nothing when nobody calls explain.

3.7 Literal truths#

The literals verity and falsity have no evidence behind them. Their testimony is simply literal. Combined with because, they let you assert a claim directly, and the message is then the whole testimony:

verity
from testimony import explain

verity |> explain |> print
(falsity because "only rectangles can be square") |> explain |> print
output
verity
  literal
falsity
  refuted: only rectangles can be square

This is mostly useful in functions that decide a claim by cases, such as the is_square function in Chapter 6.

3.8 Observing testimony#

A truth's testimony is observed when something looks at it: passing the truth to explain, returning it from a function whose caller might, storing it in a data structure and so on. A truth used only as a condition is not observed:

verity
def clamp(x) = 0 if x < 0 else 10 if x > 10 else x

Nothing in clamp can see the testimony of x < 0, so the compiler emits a plain Python comparison. This is the testimony erasure pass from Chapter 8. Its practical consequence is that you never need to avoid truths for the sake of performance. Write the clearest condition, and testimony appears where you ask for it.

3.9 Exercises#

Exercise: and/or by hand ★

Write the explain output of in_range(0) and out_of_range(11).

Exercise: double negation ★

With x = 7, what does explain print for not not (x > 3) under the not: rendering of Section 3.5? Is that output helpful? Should not not p simplify?

Exercise: claims, not complaints ★★

Rewrite these messages as claims suitable for because: "too long", "missing @", "age can't be negative".

Exercise: passwords, once ★★

Rewrite the password validator from the Chapter 1 exercises in Verity using because, so each rule appears exactly once. Write the expected explain output for "hunter2". You may assume a helper string_ops.has_digit that testifies like is_alnum.

Exercise: what does or owe you? ★★★

A verity from or reports only the first part that held. Construct an example where you would want to see every part that held. Should Verity offer a non-short-circuiting form, and what would it cost?
