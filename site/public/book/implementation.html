Section 10Implementation

This section describes the reference implementation: a compiler written in Rust and a runtime written in Python. It is informative. Other implementations need only conform to Sections 2 through 9.

10.1 Architecture#

source→lexer→tokens→parser→AST→compiler→Python
ModuleResponsibility
src/lexer.rsTokens, indentation (INDENT/DEDENT), source spans
src/parser.rsRecursive descent for statements, Pratt parsing for expressions
src/ast.rsSyntax tree types. Every node carries a span.
src/compiler.rsLowering to Python, testimony construction, erasure
src/cli.rsThe verity command (Section 9)
src/runtime.rsEmbeds runtime/truth.py via include_str!
runtime/truth.pyTruth, testimony nodes, combinators, rendering

The compiler has no run-time dependencies. The parser is hand-written rather than generated, because the grammar is indentation-sensitive and its precedence table (Section 4.1) includes non-Python operators.

10.2 Lexer#

The lexer implements Section 2. It tracks bracket depth so that line breaks inside brackets produce no NEWLINE, and maintains the indentation stack described in Section 2.3. Each token records a byte span. Spans are used both for diagnostics and to recover the exact source text quoted by comparison, universal and no-element testimony.

10.3 Parser#

Statements are parsed by recursive descent, with one function per grammar rule in Appendix A. Expressions use a Pratt parser driven by a single binding-power table, which is the precedence table in Section 4.1. Prefix forms (not, unary operators, lambdas, quantifiers) and infix forms (all binary operators, because, call, partial application) are table entries.

Operands of and/or and the messages of because are wrapped in thunks to preserve short-circuiting and laziness. The names _v, compare, and_ and so on illustrate the shape of the runtime interface. They are not final.

10.5 Runtime#

runtime/truth.py implements the Truth class, the node kinds in Section 5.1, the combinators targeted by lowering, lifting (Section 7.2) and the renderer behind explain. The compiler embeds the file at build time and writes it next to generated code, so the compiler and runtime versions always match.

10.6 Erasure pass#

Erasure runs on the AST after name resolution. For each truth-producing expression it computes whether the expression's testimony is observed, using the rules of Section 5.4. The analysis is conservative and intraprocedural: any flow it cannot follow counts as observed. Unobserved expressions are lowered to their plain Python form. VERITY_NO_ERASE=1 disables the pass, and the conformance suite is run in both modes.

10.7 Conformance#

The files examples/*.ity with expected output examples/*.expected form the conformance suite. An implementation conforms to a milestone when each example within that milestone's scope prints exactly its expected output, byte for byte, with and without erasure.
