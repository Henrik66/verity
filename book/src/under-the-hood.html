This chapter opens up the verity compiler: how source text becomes Python, what the runtime does, and how testimony disappears when nobody needs it. You don't need any of this to write Verity, but it explains why the language behaves as it does.

The pipeline

source text→ lexer→ tokens→ parser→ syntax tree→ compiler→ Python

The compiler is written entirely in Rust, as a single binary with no dependencies at run time. Each stage is a module in the repository's src/ directory: lexer.rs, parser.rs, ast.rs, compiler.rs and cli.rs.

Lexing

The lexer turns characters into tokens: names, numbers, strings, keywords such as because and forall, and operators such as |>, ..>, $ and ->. Like Python, Verity uses indentation for blocks. The lexer tracks indentation levels and emits explicit INDENT and DEDENT tokens, ignoring line breaks inside brackets, so the parser can treat blocks like bracketed groups.

Every token records its position in the source. This matters more in Verity than in most languages, because testimony quotes source text. When a comparison prints len(name) >= 3: 2 < 3, the len(name) >= 3 part was copied out of the original file using those positions.

Parsing

The parser is hand-written rather than generated by a parser-generator tool. Statements and definitions are parsed by recursive descent, where each grammar rule is a function that calls the functions for its parts. Expressions are parsed with Pratt parsing, which handles operator precedence with one table of binding strengths. Verity has unusual operators (pipes, composition, $, because, the quantifiers), so keeping all their precedences in one place is worth a lot.

A hand-written parser also makes it easier to produce good error messages, because it knows exactly what it was expecting when it got something else.

Generating Python

Most of Verity translates directly. A pipe becomes a call, def f(x) = e becomes a function that returns e, and data becomes an immutable class. The interesting part is truth. Python does not allow and, or and not to be overloaded, so the compiler rewrites them, along with comparisons, quantifiers and because, into calls to the runtime. Roughly:

def in_range(x) = (x > 0) and (x < 10)

becomes something like:

from truth import _v

def in_range(x):
    return _v.and_(
        lambda: _v.compare(x, ">", 0, src="x > 0"),
        lambda: _v.compare(x, "<", 10, src="x < 10"),
    )

A few details are worth noticing:

  • The operands of and are wrapped in lambdas, so the right side runs only if it is needed. This preserves Python's short-circuiting.
  • compare receives the source text of the expression, which is where testimony's quoted source comes from.
  • compare also implements Rule 3: if the comparison returns something that isn't a bool, it returns that value untouched.

Illustrative, not final

The names _v, and_ and compare show the shape of the translation. The actual runtime interface will be settled during the first two milestones.

The runtime

The runtime is a small Python module, truth.py. It provides the Truth class, the testimony node types, the combinators that the generated code calls, lifting of Python booleans, to_bool, and the renderer behind explain. Truth defines __bool__, which is why truths work in Python's if and while.

The runtime's source is embedded in the Rust binary at build time. When you run a program, the compiler writes truth.py next to the generated code. The compiler and its runtime therefore always match, and there is no separate package to install or keep in sync.

Testimony erasure

Building testimony costs time and memory: a compare call records operands and source text, where a raw > is a single instruction. Most truths in a program are never explained, though. They pick a branch and are gone. The erasure pass finds those truths and compiles them to plain Python booleans:

def clamp(x) = 0 if x < 0 else 10 if x > 10 else x

def clamp(x):
    return 0 if x < 0 else 10 if x > 10 else x

The analysis asks, for each truth-producing expression, whether its testimony can be observed. Testimony can escape through explain, a return value, a variable that is later used as a value, a data structure, or a call to an unknown function. If none of those paths exists, as when a comparison is used directly as an if or while condition or a match guard, the testimony is dead and the plain form is emitted. When in doubt, the pass keeps testimony. Erasure must never change what a program prints.

Erasure is the last of the five build milestones, because it is purely an optimization. Every program must behave identically with it switched off.

How the compiler is being built

The implementation proceeds in five milestones, each finished only when the repository's examples/ produce exactly their expected output:

  1. Runtime only: Truth, testimony, combinators and rendering, with tests.
  2. Tiny language: literals, def, comparisons and and/or/not, compiled to Python, plus verity run.
  3. Quantifiers and because.
  4. Coconut features, one at a time: lambdas, pipes, partial application, composition, data, match, addpattern.
  5. Testimony erasure.
