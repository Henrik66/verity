Verity is meant to be read and checked by programs as well as people: test runners, editors, CI systems and coding agents. This section specifies everything a program can rely on: JSON record formats, diagnostic codes, fixes, determinism, and plain-text documentation. [[settled]]

Principles

  • Every report has a documented machine form. Testimony has the JSON schema of Section 5.6; diagnostics, failures and test results have the records below.
  • Identifiers are stable. Diagnostic codes and reason IDs never change meaning. A retired code is never reused.
  • Output is deterministic. The same program on the same input produces byte-identical reports (Section 5.8). Durations are the only exception, and they appear only in their own fields.
  • Computed and claimed are distinguishable. Every testimony node says whether it was computed or asserted by the author.
  • Fixes are concrete. Where a diagnostic has one obvious correction, it carries it as an edit.

Records

With --json, reports are JSON Lines: one JSON object per line, UTF-8, each with a type field. verity check and verity test write records to standard output. verity run writes them to standard error, so the program's own standard output is unchanged.

A span is {"file", "line", "col", "end_line", "end_col"}, as in Section 5.6.

typeWritten byFields
diagnosticall commandscode, severity ("error" or "warning"), message, span, hint (string or null), fix (object or null)
failurerunspan (of the failing assert), testimony (a full verity.testimony/0 document)
exceptionrunexception (class name), message, traceback (list of {"file", "line", "function"}, innermost last, with .ity locations)
testtestid (FILE::NAME), outcome ("passed", "failed" or "error"), duration_ms, testimony (document or null), exception (as above, or null), stdout
summarytestpassed, failed, errors, duration_ms

A fix is {"span": span, "replacement": str}: replacing the text in span with replacement applies it. Applying every fix of a verity check run, in any order, never produces overlapping edits.

$ verity check --json hello.ity

{"type": "diagnostic", "code": "E0101", "severity": "error", "message": "`True` is not a Verity literal", "span": {"file": "hello.ity", "line": 3, "col": 9, "end_line": 3, "end_col": 13}, "hint": "use `verity`", "fix": {"span": {"file": "hello.ity", "line": 3, "col": 9, "end_line": 3, "end_col": 13}, "replacement": "verity"}}

Diagnostic codes

Codes are E for errors and W for warnings, then four digits. The first two digits give the phase: 01 lexical, 02 syntax, 03 names.

This table is extended as the compiler grows. Codes are assigned in order and never reused.

Using Verity from an agent

[[proposed]] A coding agent working in a Verity project can rely on this loop:

  1. Write or edit code.
  2. Run verity check --json. Apply every fix, address remaining diagnostics, repeat until there are none.
  3. Run verity test --json. For each failed test, read the testimony: the deciding node names the comparison and the values, a because node's reason names the rule, and its hint suggests the change.
  4. Treat nodes with "asserted": true as claims, not evidence: a claim that seems wrong may itself be the bug.

Writing checks with all_of and reason IDs makes this loop more useful, because one run reports every failing rule by name.
