Here is a question every programmer has asked a failing test: false, but why? This chapter introduces a language designed so that you never have to ask it.

The trouble with booleans

A boolean is the smallest possible answer: one bit. That is its strength, and also its problem. By the time a check has produced False, everything it learned along the way has been thrown out: which condition failed, which element of the list broke the rule, what the values were. Functional programmers call this boolean blindness. The bit tells you that something holds or doesn't, but never why.

So we rebuild the reason by hand. We add print statements, step through a debugger, or write a second function that duplicates the check just to produce an error message. Validation code in particular tends to say every rule twice: once as a condition and once as the message for when it fails.

Booleans that testify

Verity keeps the reason. Its truth type is called truth, and it has two values, verity and falsity. Every truth carries testimony:

  • a verity carries a witness, the evidence that it holds;
  • a falsity carries a refutation, the evidence that it doesn't.

You rarely build testimony yourself. Comparisons produce it, and the operators and, or and not combine it. The quantifiers forall and exists record the element that decided the answer, and because lets you state a claim in your own words. Here is a first taste:

from testimony import explain

primes = [2, 3, 5, 7, 11, 13]

all_odd = forall p in primes, p % 2 == 1
has_big = exists p in primes, p > 10

all_odd |> explain |> print
has_big |> explain |> print

if not all_odd:
    print("not every prime is odd, and Verity can tell you why")

falsity
  counterexample: p = 2 (primes[0])
    p % 2 == 1: 0 != 1
verity
  witness: p = 11 (primes[4])
    p > 10: 11 > 10
not every prime is odd, and Verity can tell you why

The falsity names its counterexample, says where it found it, and shows the comparison that failed with the actual values. The verity names the element that proves the claim. The if on the last lines treats all_odd as an ordinary condition. Truths work anywhere a Python boolean does.

Testimony that costs nothing

Carrying evidence around sounds expensive, and it would be if every comparison built a little record. But most truths in a program are only ever used to pick a branch, and nobody asks for their testimony. Verity's compiler notices this. When a truth's testimony is never observed, it compiles the check down to a plain Python boolean. You pay for testimony only where you use it. Chapter 8 describes this testimony erasure pass.

A functional Python

Testimony is Verity's distinctive idea, but most of what you write day to day is ordinary functional programming. Verity borrows its syntax from Coconut:

data Circle(r)
data Rect(w, h)

def area(Circle(r)) = 3.14159 * r ** 2
addpattern def area(Rect(w, h)) = w * h

[Circle(1), Rect(2, 3)] |> map$(area) |> list |> print

[3.14159, 6]

That small program uses an algebraic data type (data), a function defined by pattern matching and extended with addpattern, a pipe (|>) and partial application (map$(area)). Each gets its own section later.

How Verity runs

Verity is a compiled language whose target is Python:

hello.ity→ verity compiler (Rust)→ Python source + truth.py runtime→ CPython
  1. The compiler is a single program called verity, written in Rust. It reads your .ity file and translates it into Python.
  2. The generated code calls a small runtime module, truth.py, which implements truth values and testimony. The runtime is embedded in the compiler binary and written out next to the generated code, so there is nothing extra to install.
  3. CPython runs the result. This means everything in the Python ecosystem is available: the standard library, numpy, requests and anything else on PyPI.

In practice, you will use one command:

$ verity run hello.ity
